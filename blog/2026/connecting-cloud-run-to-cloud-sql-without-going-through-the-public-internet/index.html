When you deploy a Cloud Run service with a Cloud SQL database, the default setup routes traffic over the public internet. The connection is encrypted and Cloud SQL only accepts authorized connections, but there’s a better approach.

Your data doesn’t need to leave your private network. That’s where Serverless VPC Access comes in.

This article shows you exactly how to connect Cloud Run to Cloud SQL PostgreSQL using a VPC connector — keeping all traffic private, reducing latency, and following security best practices.

The Problem with Public Connectivity

By default, Cloud Run is fully serverless — it doesn’t run inside your VPC. When you connect to Cloud SQL from Cloud Run, traffic flows through:

  1. Cloud Run → Public internet
  2. Public internet → Cloud SQL public IP
  3. Authentication via Cloud SQL Proxy or SSL certificates

This works but has downsides:

  • Security concerns (traffic traverses public infrastructure)
  • Higher latency due to extra network hops
  • VPC firewall rules don’t apply (you can’t control access at the network level)
  • Compliance issues in regulated industries
  • Serverless VPC Access solves this by creating a connector that bridges Cloud Run to your VPC — letting your Cloud Run service act like it’s running inside the network.

What is Serverless VPC Access?

Serverless VPC Access is a feature that allows serverless environments (Cloud Run, Cloud Functions, App Engine) to send requests to resources in a VPC network using internal IP addresses.

The connector works by provisioning a dedicated /28 subnet (16 IPs) in your VPC and spinning up e2-micro VMs that forward traffic between Cloud Run and your network. You control which traffic uses it via the —- vpc-egress flag:

  • -private-ranges-only — Only RFC 1918 addresses (10.x, 172.16.x, 192.168.x) route through the connector (default)
  • all-traffic — All egress routes through the connector (needed for VPN/Interconnect scenarios)

A few things worth knowing: connectors are regional, require their own /28 that can’t be shared, and multiple Cloud Run services can reuse the same connector. IPv6 and Shared VPC (unless the connector is in the host project) are not supported.

What We’re Building

  • A VPC named vpc-main with subnet in us-central1
  • A Cloud SQL PostgreSQL 14 instance with private IP only (no public IP)
  • A Serverless VPC Access connector named my-connector
  • A Cloud Run service named my-api running a Flask app that queries the database
  • A test VM to verify connectivity

Architecture Overview

Key components:

  • Serverless VPC Access Connector: A managed resource that provisions a /28 subnet (16 IPs) in your VPC. Acts as a bridge allowing Cloud Run to send traffic into the VPC network using private IP addresses.
  • Cloud SQL Private IP: The database instance gets an IP from your VPC’s address range via Private Service Connection. No public IP means zero internet exposure.
  • VPC Egress Setting: Configured as private-ranges-only — only RFC1918 traffic (10.x, 172.16.x, 192.168.x) routes through the connector. Public internet traffic goes direct.
  • Private Service Connection: Google-managed peering that allocates Cloud SQL IPs from your VPC without consuming subnet space.

Security benefits:

  • Database traffic never traverses public internet
  • Cloud SQL instance inaccessible from outside your network
  • VPC firewall rules apply to connector traffic
  • VPC Flow Logs capture all connector activity for auditing

Prerequisites

  • GCP project with billing enabled
  • gcloud CLI configured
  • Terraform >= 1.0
Cost: around $2–3 per day for Cloud SQL (cheapest tier). Destroy resources after testing to avoid charges.

Step 1: Clone and Setup

Clone the repository:

git clone https://github.com/misskecupbung/gcp-serverless-vpc-access.git
cd ~/gcp-serverless-vpc-access/

Step 2: Enable APIs

Set your project ID and enable required APIs:

export PROJECT_ID="your-project-id"
gcloud config set project $PROJECT_ID

gcloud services enable compute.googleapis.com
gcloud services enable sqladmin.googleapis.com
gcloud services enable vpcaccess.googleapis.com
gcloud services enable run.googleapis.com
gcloud services enable servicenetworking.googleapis.com
gcloud services enable cloudresourcemanager.googleapis.com
gcloud services enable cloudbuild.googleapis.com

These APIs are required for:

  • compute.googleapis.com: VPC networking and Cloud NAT
  • sqladmin.googleapis.com: Cloud SQL instance management
  • vpcaccess.googleapis.com: Serverless VPC Access connector
  • run.googleapis.com: Cloud Run service deployment
  • servicenetworking.googleapis.com: Private Service Connection for Cloud SQL
  • cloudresourcemanager.googleapis.com: Project metadata and resource management
  • cloudbuild.googleapis.com: Container image building

API enablement takes 1–2 minutes.

Step 3: Build the Container Image

Before running Terraform, build and push the Flask app container. Terraform will deploy this image to Cloud Run:

cd ~/gcp-serverless-vpc-access/app/

gcloud builds submit --tag gcr.io/$PROJECT_ID/my-api

The build takes about 1–2 minutes. Once complete, the image is stored in Google Container Registry.

Step 4: Configure Terraform Variables

Navigate to the Terraform directory:

cd ~/gcp-serverless-vpc-access/terraform/
cp terraform.tfvars.example terraform.tfvars

Update the project ID:

sed -i 's/your-project-id/'$PROJECT_ID'/g' terraform.tfvars

Verify the configuration:

cat terraform.tfvars

Step 5: Deploy Infrastructure with Terraform

terraform init

Generate an execution plan:

terraform plan

Apply the configuration:

terraform apply

Type yes when prompted.

This creates:

  • VPC with subnet (10.0.0.0/24) in us-central1
  • Private Service Connection for Cloud SQL
  • Cloud SQL PostgreSQL instance with private IP only
  • Serverless VPC Access connector
  • Cloud Run service connected to the VPC connector
  • A test VM (for verification)
  • Cloud NAT gateway (VM needs internet for package downloads)

The apply takes 8–12 minutes because Cloud SQL provisioning is slow.

Step 6: Verify Resources from Console

VPC Network

Navigate to VPC network → VPC networks in the console:

You should see vpc-main with:

  • Subnet subnet-main in us-central1 with range 10.0.0.0/24
  • A reserved IP range for Private Service Connection (for Cloud SQL)

Serverless VPC Access Connector

Go to Serverless VPC Access in the console:

The connector should show:

  • Name: my-connector
  • Region: us-central1
  • IP range: 10.8.0.0/28
  • Status: Ready
  • Min instances: 2, Max instances: 3

Cloud SQL Instance

Navigate to SQL in the console and click on my-instance:

Key details to verify:

  • No public IP address listed
  • Private IP in the 10.x.x.x range
  • Connection name visible

Cloud Run Service

Go to Cloud Run and click on my-api:

Verify:

  • Service is deployed and healthy
  • VPC connector: my-connector is attached
  • VPC egress: Private ranges only
  • Region: us-central1

Test VM

Navigate to Compute Engine → VM instances:

The VM should have:

  • No external IP (fully private)
  • Internal IP in the 10.0.0.x range
  • Zone: us-central1-a

Step 7: Verify Cloud SQL Private Connectivity

Verify the Cloud SQL instance has only a private IP using gcloud:

DB_IP=$(terraform output -raw cloud_sql_private_ip)
echo "Cloud SQL Private IP: $DB_IP"

gcloud sql instances describe my-postgres \
  --format="value(ipAddresses)"

You should see only a private IP (something like 10.x.x.x). No public IP.

This confirms the database is not accessible from the internet. Only resources inside the VPC can reach it.

Step 8: Test Cloud Run → Cloud SQL Connection

Get your Cloud Run service URL:

SERVICE_URL=$(terraform output -raw cloud_run_url)
echo "Cloud Run URL: $SERVICE_URL"

Test the root endpoint:

curl -s $SERVICE_URL | jq .

You should see:

{
  "service": "my-api",
  "status": "healthy"
}

Now test the database connection:

curl -s $SERVICE_URL/db | jq .

If everything works, you’ll see PostgreSQL version information and confirmation of the database connection.

{
  "database": "connected",
  "host": "10.126.0.3",
  "version": "PostgreSQL 14.x on x86_64-pc-linux-gnu, compiled by gcc..."
}

This confirms that:

  1. Cloud Run is routing through the VPC connector
  2. The connector has access to the VPC
  3. Cloud SQL is reachable via private IP
  4. PostgreSQL authentication works

Step 9: Verify Connectivity from Test VM

Let’s double-check that the Cloud SQL instance is truly private by connecting from our test VM:

DB_IP=$(terraform output -raw cloud_sql_private_ip)

gcloud compute ssh test-vm \
  --zone=us-central1-a \
  --tunnel-through-iap \
  --command="PGPASSWORD=changeme123 psql -h $DB_IP -U appuser -d appdb -c 'SELECT version();'"

This proves the database is accessible from inside the VPC but not from the outside.

Cleanup

Destroy resources when done:

cd ~/gcp-serverless-vpc-access/terraform/
terraform destroy

Type yes to confirm.

If you encounter Failed to delete Service Networking Connection.

This happens because the VPC peering connection (servicenetworking.googleapis.com) created by Private Service Connection is still active. Delete it manually:

Wait 30 seconds, then run terraform destroy again.
